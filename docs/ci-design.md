# GitHub Actions による自動検証の設計書

作成: 2026-09-06 / 対象リポジトリ: asa-ken/research-harness

## この文書の位置づけ

配管（GitHub Actions）を「なぜこう作ったか」を残すための設計書。
実装だけが残ると、後から見た人（未来の自分を含む）が前提を知らないまま
変更してしまう。この文書は結論ではなく**経緯と前提**を書く。

---

## 1. なぜ配管が必要か（背景）

### 解こうとしている問題

2026-09-05 の ROK 案件で、次の失敗が起きた。

- Skill は起動し、SKILL.md も読み込まれていたが、**チェック機構が一度も実行されないまま**
  5本のレポートが納品された
- 台帳（ledger.jsonl）が存在しないのに、レポートには E-ID（証拠番号）が振られていた。
  実体は「その場で採番した連番」で、第三者が辿れない
- E-ID 表記が「検証済み」の外観を与え、Skill が防ごうとした失敗をむしろ助長した

### なぜ既存の対策では防げなかったか

SKILL.md には「検証はスクリプトが行い、Claudeは判定しない」と明記されている。
それでも防げなかったのは、**スクリプトを実行するかどうかを決めているのが Claude 自身**
だったから。文章による指示は、読んで従うと判断したときにしか効かない。
実際、Claude は SKILL.md に存在しない「軽量運用」という概念を自分で作り、
ルールごと迂回した。

2026-09-01 に I-105 対策として「前工程の実行証跡が無ければ次に進まない」を
workflow.md に明記したが、これも**手順書への記述**であり、同じ迂回経路が残る。

### 配管が解決する部分

GitHub Actions は、Claude の判断を経由せずに実行される。
リポジトリにファイルが push された時点で、GitHub 側のサーバーが機械的に検査を走らせる。
Claude が「今回は飛ばそう」と判断しても関係がない。

**ただし、これは「強制」ではなく「露見の保証」である。**
Claude が最初から何も push しなければ、配管は動かない。
配管が保証するのは「push されたものは必ず検査され、結果が記録される」ことまで。

## 2. 設計判断とその前提

### 判断1: 案件を Skill と同じリポジトリに置く

**決定**: `research/` を research-harness リポジトリ内に置く。

**前提**: 検査スクリプト（scripts/）と案件（research/）が同じ場所にあれば、
配管がスクリプトを呼び出して案件を検査する流れが素直に書ける。
別リポジトリだと検査のたびにスクリプトを持ってくる手間が増える。

**さらに重要な前提: 追跡性。** 配管が証明しようとしているのは
「レポートが本当に検査を通ったか」だが、**検査したスクリプトのバージョンが
特定できなければ、その証明は不完全**になる。後から「あの時点の検査に穴があった」と
判明したとき、影響範囲を追えないためである。同一リポジトリなら案件と検査コードが
同じコミットに紐づくので、この問題は構造的に消える。

**この前提が崩れる条件**:
- 案件数が増えてリポジトリが重くなり、clone やCI実行が実用に耐えなくなったとき
- 案件に第三者と共有できない情報が入り、Skill 本体と公開範囲を分けたくなったとき
- **Skill 本体を公開し、案件は非公開に保ちたくなったとき**
  （上の条件と似ているが、こちらは Skill 側を外に出す動機が起点。
  分ける場合は下記の追跡性の問題が再発するため、`receipt_*.json` への
  commit hash 併記などの補償策とセットで判断すること）

#### 経緯: 一度分割し、翌日に統合し直している

この判断は、**当初この経緯を把握しないまま書かれた**。設計書の不備である。
実際には次の経過をたどっている。

| 日付 | 出来事 |
|---|---|
| 2026-09-05 | Claude Code 側とチャット側で別々に話が進み、`skill/` が2リポジトリに重複（`stock-research` が旧版26ファイル/テスト64件、`research-harness` が新版29ファイル/テスト157件）。重複解消のため `stock-research` から `skill/` を削除し、「`research-harness`=Skill本体 / `stock-research`=案件」と役割を分けた |
| 2026-09-06 | 上記の分割を取り消し、`research/` を `research-harness` に統合。この判断1の内容に実態を合わせた |

**分割は積極的な設計判断ではなかった。** 二重管理を解消する過程で、
結果的に役割が分かれただけである。したがって「崩れる条件」に挙げた
公開範囲の分離のような理由には該当しない。

統合の決め手は上記の**追跡性**である。分割していた間は、案件の commit を見ても
そのとき使った Skill のバージョンを特定できず、補償策として
「`receipt_*.json` に `research-harness` 側の commit hash を併記する」案が
未実装のまま残っていた。統合によりこの問題は解消し、補償策も不要になった。

**検討して採らなかった案**: 分割を維持したまま `case-verify.yml` を案件側の
リポジトリに置き、CI 内で `research-harness` を clone する。
採らない理由は、「どのバージョンを clone したか」が再び曖昧になり、
追跡性の問題が形を変えて残るため。

分割時点の詳しい記録は `docs/git-migration-design.md` にある。

### 判断2: 失敗しても「記録するだけ」（ブロックしない）

**決定**: 検査失敗時、GitHub 上に赤いバツを記録するが、push 自体は成功させる。

**前提**: いきなりブロックすると、作業途中の案件を一時保存したいだけのときにも
止まってしまう。まず「結果が記録される」状態を作り、運用に慣れてから強める。
これは Skill 本体で採った「まず WARN、定着したら FAIL」と同じ段階導入の考え方。

**この前提が崩れる条件**:
- 記録するだけでは無視されるようになり、赤いバツが常態化したとき
  → その時点でブロック（ブランチ保護ルール）に強める

### 判断3: 全案件を毎回検査する

**決定**: push のたびに `research/` 以下の全案件を検査する。

**前提**: 変更された案件だけを特定する処理は複雑で、最初の実装として躓きやすい。
検査自体は1案件あたり数秒で終わるため、当面は全件実行でも実用的。

**この前提が崩れる条件**:
- 案件数が増えて CI の所要時間が実用の限界（目安: 5分）を超えたとき
  → 変更された案件だけを検査する方式に改良する

### 判断4: Skill健全性チェックと案件検証を別ワークフローにする

**決定**: `skill-tests.yml`（Skill自体のテスト）と `case-verify.yml`（案件の検証）を分ける。

**前提**: 動作するトリガーが違う（前者は scripts/tests の変更、後者は research/ の変更）。
一つにまとめると、案件を上げただけで Skill のテストが走るなど、無関係な実行が増える。
また、失敗したときにどちらの問題かが即座に分かる。

**この前提が崩れる条件**:
- 両者の依存関係が強くなり、片方だけ実行しても意味がなくなったとき

## 3. ワークフローの仕様

### 3-1. skill-tests.yml（実装済み・稼働中）

**目的**: Skill 自体（検査スクリプト）が壊れていないかを自動確認する。

| 項目 | 内容 |
|---|---|
| トリガー | main への push（`scripts/**`, `tests/**` 変更時）、Pull Request、手動実行 |
| 実行環境 | ubuntu-latest / Python 3.12 / openpyxl 導入 |
| 実行内容 | `python3 tests/run_tests.py` |
| 成功条件 | 全テスト成功 |

**openpyxl を導入する理由**: Excel 実ファイル検証の1件が openpyxl 未導入だと
スキップされ、母数が 157 → 156 に変わる。CI 環境で必ず導入することで件数を固定し、
「環境によって数字が変わる」混乱を防ぐ。

### 3-2. case-verify.yml（これから実装）

**目的**: 調査案件がハーネスの検査を通っているかを自動確認する。

| 項目 | 内容 |
|---|---|
| トリガー | main への push（`research/**` 変更時）、Pull Request、手動実行 |
| 実行環境 | ubuntu-latest / Python 3.12 / openpyxl 導入 |
| 実行内容 | 各案件に対し `run_gate.py <案件> --gate all` → `verify_gate.py <案件> --gate B` |
| 成功条件 | 全案件で両方が成功 |

**実装上の要件**:

1. **失敗しても打ち切らない**: 個々の案件で検査が失敗しても、そこで止めず全案件を
   実行しきる。全件終了後に、1件でも失敗があればワークフロー全体を失敗にする。
   （途中で止まると、他の案件の状態が分からなくなるため）

2. **案件が無くてもエラーにしない**: `research/` が存在しない、または案件が
   1つも無い場合は「検査対象なし」として正常終了する。
   （配管導入直後は案件が存在しないため）

3. **ログで案件を識別できる**: どの案件を検査しているか、どこで失敗したかが
   ログから分かるようにする。日本語のメッセージを添える。

4. **アクションは最新版**: `actions/checkout@v5`, `actions/setup-python@v6`
   （v4/v5 は Node.js 20 依存で非推奨警告が出るため）

## 4. この配管で検証できる範囲・できない範囲

配管を過信すると、「検証されていない部分を検証済みと誤解する」という、
ROK 案件と同種の失敗を招く。範囲を明示しておく。

### 検証できる（機械的に白黒つく）

| 対象 | 内容 |
|---|---|
| Skill の健全性 | 検査スクリプトが壊れていないか |
| 台帳⇔原文 | 引用が原文に実在するか、原文が差し替わっていないか（check_a） |
| 台帳⇔レポート | E-ID が台帳に実在するか、数値が一致するか、無出典文が無いか（check_b） |
| 実行証跡 | 検査を実際に通したか、通した後にレポートを書き換えていないか（verify_gate） |
| ステータス語彙 | 「不明」でぼかしていないか（lint_status） |
| 鮮度 | 公開日が鮮度基準より古くないか（check_freshness） |

**ROK 案件の失敗（台帳なしで E-ID を振る、検査を飛ばす）は、ここで機械的に暴ける。**

### 検証できない（人間の判断が必要）

| 対象 | なぜ機械化できないか |
|---|---|
| 原文そのものの正しさ | 引用の一致は見れるが、原文の情報が事実として正しいかは判定できない |
| 引用の意味的妥当性 | 文字は一致するが文脈を無視した切り取り（「好調だが来期減速」の前半だけ引用など）は見抜けない。→ 独立レビュー（GC）で人が行う |
| 評価軸・仮説の妥当性 | 「そもそも容量密度で測るのが誤り」のような問いの立て方の誤りは判定できない |
| 実質的な鮮度 | 日付は新しいが内容が既に古びている、は判定できない |
| 調査範囲の網羅性 | リストの項目を集めたかは見れるが、リスト自体の見落としは分からない |
| 文書と検査機構の整合 | `references/` 配下の参照ファイルには「E-IDを持つ」「ソース階層を守る」など、スクリプトの検査内容と整合すべき記述が含まれるが、文書の記述が検査機構と矛盾していないかを確かめる仕組みが無い |

**一言でいえば: 配管は「嘘と不整合」を防げるが、「筋の悪さ」は防げない。**

## 5. 記録の方針（2026-09-06 合意）

配管が出す検査結果や、それへの対応を記録する際の方針。

### 結論ではなく経緯と前提を書く

「問題なし」と結論だけ書いた記録は、次に同じ検出が出たときに
中身を見ずに「前回OKだったから」と処理させる。記録が考えることの代わりになる。

各記録には次を含める:

- 何が検出されたか（検査コードと内容）
- どう判断したか
- **その判断が依拠した前提**
- **その前提が崩れる条件**（何が変われば見直しが要るか）

「前提が崩れる条件」は、ハーネスが仮説に崩壊条件を書くのと同じ発想。
前提が明示されていれば、次に読むとき「この前提は今も成り立つか」と問える。

### ズレを見つけたら止まって相談する

**ルール**: ハーネスの見直しや改修を行う際、過去の対応記録に書かれた
「経緯・前提」と現在の状況との間にズレを見つけたら、そこで作業を止め、
Ken と方針を整理してから進める。ズレを Claude の判断で解消しない。

**なぜ日数による期限を採らないか**:
「6ヶ月経ったら見直す」のような期限方式は、期限が来ても実際にはズレていない場合に
無駄な確認を生み、逆に期限前にズレていても見直さない抜け穴を作る。
形式的な基準が実質的な判断の代わりになる構図は、
「検査を通したという形式が検証の実質の代わりになる」ROK 案件の失敗と同型。
**ズレが実際に発生したことを引き金にする**方が、無駄も抜け穴もない。

**このルールの限界（正直な注記）**:
これは Claude が守ることを前提にしたルールであり、強制力はない。
Claude が「今回はズレていない」と誤判断すれば素通りする。
ただし記録に「前提」と「崩れる条件」が明記されていれば、
ズレの検知は機械的にやりやすくなり、素通りする確率は下がる。

## 6. 今後の課題（未着手）

- **案件を上げる運用の定着**: 現状、チャットからの GitHub 書き込みは
  Anthropic 側の既知の不具合（403 Resource not accessible by integration）で
  塞がれており、Claude Code 経由でしか push できない。
  チャットからの書き込みが復旧すれば、この手間は解消する
- **文書と検査機構の整合が未検証**: `references/` 配下の参照ファイルには
  「E-IDを持つ」「ソース階層を守る」など、スクリプトの検査内容と整合すべき
  記述が含まれる。しかし文書の記述が検査機構と矛盾していないかを確かめる
  仕組みは無い。`tests/run_tests.py` はスクリプトの動作しか見ていないため、
  たとえば参照ファイルに「技術調査では図表のE-IDを省略してよい」と誤って
  書かれても、テストは通ってしまう
- **記録の仕組み化**: 検査結果への対応記録を、どこにどう残すかの様式は未設計。
  配管が動いて実際の検査結果が出てから設計する
- **ブロックへの格上げ**: 判断2の通り、記録が無視されるようになったら
  ブランチ保護ルールでブロックに強める
- **変更案件のみの検査**: 判断3の通り、CI 所要時間が実用限界を超えたら改良する
