# evidence.md — 証拠台帳の運用規則

## 1証拠 = 1行（JSONL）

| フィールド | 必須 | 内容 |
|---|---|---|
| `eid` | ○ | `E-0001` 形式。採番は `build_ledger.py` に任せる |
| `source_id` | ○ | `sources.json` に存在すること |
| `claim_type` | ○ | `fact` / `negative`（非公表の確認）/ `forecast`（会社予想）/ `opinion`（第三者見解） |
| `quote` | ○ | **原文の完全一致部分文字列**。改変・省略記号の挿入・全角半角変換をしない |
| `char_start` / `char_end` | △ | 空なら `build_ledger.py` が自動補完（複数一致なら要指定） |
| `fact` | ○ | 自分の言葉での正規化。数値は単位・期を明示 |
| `value` | △ | 数値がある場合 `{number, unit, period}`。比率は `unit:"%"` |
| `basis_date` | ○ | その情報の**基準日**（決算期末や発表日。取得日ではない） |
| `confidence` | ○ | 高/中/低。T5以下のソースは中以下、T6は低固定 |
| `tags` | ○ | 調査カテゴリ（後述）から選ぶ |
| `note` | | 前提・注記（会計基準変更、非継続事業の除外など） |
| `subject` | △ | 主張の主体（セグメント名・子会社名・製品名等）。**セグメント別の数値を扱うときは必ず書く**。台帳とレポートの主体が一致するかをB19が照合する統制語彙になる |
| `value.basis_scope` | △ | 連結/単体・累計/単四半期などの区分。法人・期間の粒度を持つ数値には書く。A20が引用と照合する |

## タグ（調査カテゴリ・10区分）

`ビジネスモデル` / `財務.実績` / `財務.株価指標` / `財務.健全性` / `市場環境` / `競争環境` /
`技術` / `ガバナンス` / `リスク` / `株主還元`

このタグでレポートのセクションと台帳が対応するため、**タグの取りこぼし＝章の空白**として検出できる。
本ハーネス内で完結する区分であり、外部システムの分類体系とは独立している。

## claim_type の使い分け

- `fact`: 実績値・確定した事象。過去形で書ける
- `forecast`: **会社予想・ガイダンス**。事実ではないが「会社がそう言った」は事実。
  レポートでは必ず「会社予想」と明記する（自分の推定と混ぜない）
- `opinion`: アナリスト見解・報道の評価部分。`confidence:低`。結論の根拠には使わない（背景説明のみ）
- `negative`: 「探したが記載が無い」ことの証拠。`quote` にはその文書の該当章の見出しなど
  **探した場所を示す原文**を入れる。これが `[非公表]` の成立条件になる

## ソース階層と矛盾処理

T1 法定開示 ＞ T2 発行体一次資料 ＞ T3 公的統計 ＞ T4 データベース ＞ T5 主要メディア/アナリスト ＞ T6 その他

矛盾が出たときにやること:
1. **消さない**。両方を台帳に残す（`note` に相互参照）
2. レポートには上位ソースの値を採用し、下位との差分と採用理由を脚注で書く
3. 同一Tier内で矛盾する場合は、より新しい `basis_date` を採用。それでも割れるなら
   `[推定|確信度:低]` に落として両論併記する

**よくある「見かけの矛盾」**: 連結/単体、IFRS/日本基準/US GAAP、暦年/会計年度、
継続事業のみ/全体、為替換算基準、調整後（non-GAAP）指標の定義差。
値が合わないときは、まずこの6つを疑う。`note` に基準を明記すれば矛盾ではなくなる。

## 期（period）の裏付け

法定開示は「当連結会計年度」と書き、具体的な期を明示しないことが多い。
証拠ごとにnoteで期を説明するのは摩擦が大きいので、**文書全体の対象期を
`sources.json` の `period_context` に一度だけ宣言する**。

check_a の判定は3段階:

| 状況 | 判定 |
|---|---|
| 引用・basis_datetime・period_context のいずれかと一致 | OK |
| 引用が「前連結会計年度」「次期」等の相対表現／`claim_type:forecast` | WARN（noteに根拠を書く） |
| period_context と食い違い、相対表現でもない | **FAIL** |
| 引用に別の期が明示されているのに違う期を記録 | **FAIL** |

## 株価・株価指標（T4）の時点整合

株価は他の証拠と性質が違う。**日付だけでは足りず、時点が要る。**
ザラ場中に取った値は当日終値ではないし、翌日には別の値になる。

- `basis_datetime` を必須にする（`2026-08-21T15:30+09:00` のように時刻まで）。
  `basis_date` だけの株価証拠は check_a が FAIL にする

### 株価は終値ベースに固定する

ザラ場値・PTS・リアルタイム値は日中に動くため、**後から同じ数字を再現できない**。
検証可能性を担保するために終値に固定する。

| 調査時点 | 採用する値 |
|---|---|
| その日の場が引けている | **当日終値** |
| 場中・寄り前 | **前営業日終値** |

- `note` に「終値」と明記する。無ければ check_a が FAIL
- 引け時刻より前の `basis_datetime` は終値になり得ないため FAIL（東証15:30 / 米国16:00現地）
- 土日の日付は WARN。**祝日・半日立会はスクリプトで判定できない**ので、
  連休明けなどは前営業日を自分で確認する

**PER・PBR等の指標は、分子と分母の時点と定義が違う。** ここを混ぜたまま「割安」と書くのが、
バリュエーション記述で最も起きやすい事故なので、`note` に必ず基準と対象期を書く。

### 採用する指標は「コンセンサス予想」と「実績」

**会社予想ベースの指標は採用しない。** 会社予想は保守的にも強気にも置かれ、経営の姿勢が混ざるため、
市場が織り込んでいる水準を測る目的には合わない。会社予想EPS自体は `claim_type:forecast` として
台帳に持ってよいが、PERの分母には使わない。

| 指標 | 基準 | noteの例 |
|---|---|---|
| PER（予想） | **コンセンサス予想EPS** | コンセンサス予想EPS(27年3月期)基準、株価は2026-08-21終値、提供元○○ |
| PER（実績） | 直近実績EPS | 実績EPS(26年3月期)基準、株価は2026-08-21終値 |
| PBR | 実績BPS | 実績BPS(26年3月期末)基準 |
| 配当利回り | 実績 または コンセンサス予想 | 実績DPS(26年3月期)基準 |

会社予想しか取れなかった場合は、その指標を `[調査不可|PRICED_DB or LOGIN|依頼:R-xxx]` とし、
コンセンサスの提供元をユーザに依頼する。**会社予想で代用して黙って進めない。**

**コンセンサスは無料で取れないことが多い**（ログイン必須・有料プラン）。
依頼が発生する前提で調査計画を立て、G1でまとめて依頼する。

## 複数期をまとめた要約表の扱い

5期推移表・ファクトシート・統合報告書の業績ハイライトは便利だが、会計基準変更・セグメント再編・
遡及修正の後に**過去の数値が原資料と食い違う**ことがある。

- 要約表から引く場合は `note` に「会社作成の要約表」である旨と、組替え・遡及修正の有無を書く
- `confidence` は原資料から取る場合より1段下げる（高→中）
- **結論に効く期の数値は原資料（有報・短信）で裏を取る。** 全期を裏取りする必要はない

## Critical判定基準について（設計上の注記）

「重要度C（Critical）」の判定基準は、**案件ごとに`scope.md`で個別に決める**。
外部の参照設計（他業種向け調査Skill等）が持つ固定のCritical項目リストは、
そのドメインの重要項目定義であり、株式調査に転用しない。判定基準は常に
「これが無いと結論が変わるか」という一点で、案件ごとに考え直す。

（過去に検討した参照設計はエネルギーサービス調査に特化したもので、
Critical項目の固定リストはそのドメイン専用だった。仕組み——飽和基準・
探索ログ・重要度による扱いの差——は取り込んだが、リストの中身は取り込んでいない）

## 読解範囲のルール（どこまで読んでから引用するか）

機械チェックは2段構え。A18は引用の前後100字（直近の切り取り検出）、
A19は文書冒頭側の前提条件の記載と引用位置の乖離（離れた場所にある前提の見落とし検出）。
**それでも文書全体の意味的な整合は機械では閉じない。人が範囲を担保する。**
証拠の種類ごとに、引用前に読む範囲を決めておく。

| 証拠の種類 | 最低限読む範囲 | 理由 |
|---|---|---|
| 数値（売上・利益・数量など） | **その数値が載る表または節の全体** | 単位・脚注・注記が表の外にあることが多い |
| セグメント情報 | **セグメント注記の全体** | 調整額・内部取引消去が末尾にまとまっている |
| `claim_type:negative`（非公表の確認） | **該当章の全体** | 「無いこと」は一部を見ただけでは言えない |
| 会社予想・ガイダンス | **前提条件の記載を含む節** | 為替前提・数量前提が別段落にある |
| リスク記載 | **その項目の全文** | 条件・限定が後半に来る |
| Webページ | **同一ページ全体**（少なくとも当該セクション全体） | 見出しと本文で主体が違うことがある |
| PDF | **抽出テキスト全体を保存**した上で、引用箇所の前後は最低1段落 | ページ跨ぎで文が分断される |

**PDFは必ず全文を `raw_text/` に保存し、確認するときも全文を通読する。**
該当ページだけを切り出して保存・確認しない。前提条件が冒頭、根拠が後半にあるという
配置は開示文書で頻出するため、抽出漏れは即ち前提の見落としに直結する。
（`capture_source.py` はページ境界を `<<<PAGE n>>>` として保持する。A19がこの
raw_text全体を対象に前提ゾーンを走査する）

**Webページはページ全体を保存・確認する。** アクセス日時とURLを記録した上で、
見出しから末尾まで本文全体を保存する。URLだけを記録して本文を保存しないのは不可。
ページ内リンクで前提条件が別セクションに分離されている場合、そのセクションも保存する。

読んだ範囲は `note` に書かなくてよいが、**負の証拠（非公表）だけは
「どの章のどこまでを見たか」を `fact` に書く**。これが `[非公表]` の成立条件になる。

## 確信度を下げるべき兆候（レッドフラグ）

以下が観測されたら、その論点の `confidence` を1段下げ、`note` に理由を書く。
**強気の物語ほど、これらを見落としやすい。**

| 兆候 | 見る場所 | なぜ効くか |
|---|---|---|
| 在庫・売掛金が売上より速く増えている | BS / CF計算書 | 売れているのではなく積み上がっている可能性 |
| 希少性を主張しているのに粗利率が改善していない | セグメント別損益 | 本当に希少なら価格に出るはず |
| **経営陣がテーマの言葉を使うのに、セグメントデータが変わっていない** | 説明会資料 vs セグメント情報 | 語りと実態の乖離。最も見落としやすい |
| 顧客名が非開示で、収益インパクトも曖昧 | 「主要な顧客」の記載 | 検証できない期待が価格に入っている |
| 機会が収益化する前に資金調達が必要 | CF計算書 / 増資・社債の開示 | 希薄化リスク。時間軸が合っていない |
| 株価上昇の主因がSNSや話題性 | 出来高・値動きと開示の時系列 | 需給要因を業績要因と誤認しやすい |
| 論拠が単一の顧客に関する噂 | 情報源の階層 | T5〜T6のみを土台にした仮説 |

**3つ目が最重要。** 「AI関連」「データセンター向け」と語りながら、
セグメント売上構成も利益率も動いていない場合、テーマ関連度は言葉だけの可能性が高い。
`ledger` に**語り（決算説明資料の文言）と実績（セグメント情報の数値）を別々のE-IDで登録**し、
レポートで両方を並べれば、乖離が読み手に見える。

これらは機械判定できるものもある（在庫・売掛の伸び率など）。
検出できた場合は該当証拠の `note` に「レッドフラグ:～」と明記する。

## 引用の記録方法（識別語＋位置）★重要

**台帳に原文を転記しない。** 開始・終了の短い識別語だけを記録し、
実際の引用文はスクリプトが `raw_text/` から読み出す。

| フィールド | 内容 | 制限 |
|---|---|---|
| `anchor_head` | 引用範囲の**開始**を示す識別語 | 40字以内 |
| `anchor_tail` | 引用範囲の**終了**を示す識別語 | 40字以内 |
| `char_start` / `char_end` | 解決された位置 | `build_ledger.py`が自動記入 |

```json
{"eid":"E-0007","source_id":"S-001","claim_type":"fact",
 "anchor_head":"データセンタ向け需要の拡大を背景に",
 "anchor_tail":"980億円となりました。",
 "fact":"会社説明: 情報通信の増収要因はデータセンタ向け需要拡大",
 "basis_date":"2026-08-07","confidence":"高","tags":["市場環境"]}
```

**なぜこの形式か**: 原文を書き写す行為自体が引用制限に抵触するため。
識別語は「原文の再現」ではなく「位置の索引」であり、
間の本文は機械取得された `raw_text/` の中にあるだけで、転記されない。
**検証の厳密さはむしろ上がる**（毎回原文から読み直すので、転記ミスの経路が消える）。

### 識別語の選び方

- **一意に決まるものを選ぶ。** 同じ書式が前年同期と当期で並ぶ表では、
  数値を含めるなど特徴的な部分を使う（A02が曖昧性を検出する）
- 短すぎると曖昧になり、長すぎると制限に触れる。**10〜25字程度**が目安
- 曖昧性が解消できない場合は `char_start` を明示して絞る

### 1ファイルから複数箇所を参照する場合

**箇所ごとに別のE-IDを立てる。** 台帳側は位置参照なので件数に制限はない。
1つの決算短信から、セグメント表・損益計算書・貸借対照表…と何件でも取れる。

### レポート本文での引用ルール（台帳とは別）

| | 制限 |
|---|---|
| 台帳の証拠（識別語＋位置） | 制限なし。箇所ごとにE-IDを分ける |
| レポート本文の**直接引用**（鉤括弧付き） | **同一出典から1回まで、15語未満** |
| レポート本文の**パラフレーズ** | 制限なし（**原則こちらを使う**） |

レポートは自分の言葉で書き、E-IDで根拠を指す。原文の鉤括弧引用は、
その表現自体が論点になる場合に限る（B10が重複引用を検出する）。

## 引用と著作権

- `quote` は検証用のローカル作業データ。原文一致が要件なのでここは省略しない
- **レポート本文は原則パラフレーズ**。直接引用は1ソースにつき短い1箇所まで
- 記事構成のなぞり（見出しの再現・段落順の再現）をしない。要点を自分の構造で書く
- 有料記事・レポートの実質的な代替になる分量を書かない

## やってはいけない

- 検索スニペットだけを根拠に台帳を書く（原文全体を保存してから引く）
- 「概ね◯◯億円」のような丸めを `value.number` に入れる（原文の値を入れ、丸めはレポート側で）
- 複数の文をつなげて1つの `quote` にする（離れた箇所は別E-IDに分ける）
- 翻訳した文を `quote` に入れる（原文は原語のまま。訳は `fact` に書く）
