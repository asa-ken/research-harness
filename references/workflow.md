# workflow.md — フェーズ別手順

## P0: スコープ確定（ゲートG0）

ユーザに以下を確認してから着手する。ここを曖昧にしたまま走ると、後半で調査全体をやり直すことになる。

1. **対象**: 銘柄（ティッカー/証券コード）／業界／マクロテーマ のいずれか、複数可
2. **問い**: 何を判断したいか（新規エントリー / 継続保有 / ペアの相方選定 / 仮説の検証 など）
3. **期間軸**: 直近四半期のみ / 5期トレンド / 中期計画まで
4. **深度**: サマリ（1ゲートで完了）/ 標準（2〜3ゲート）/ 深掘り（テーマ別に分割）
5. **既存の持ち物**: すでに持っているPDF・メモ・過去分析（あれば最初に受け取る＝取得コスト削減）

出力: `research/<case>/scope.md`（対象・問い・仮説の初期形・必要証拠リスト）

6. **採用する問いの選択** — 初期仮説を立てた**後**に `references/questions.md` を開き、
   今回使う問いをIDで選ぶ（共通コアから5〜10問が目安、`Q-R4`は必須）。
   対象がデータセンター・AI関連ならテーマアドオンも検討し、その場合は
   供給側・持続性の問い（Q-A9〜Q-A12）から最低1問を入れる。
   選択結果は `scope.md` の「採用した問い」に記録する

**必要証拠リストには重要度（C=Critical / N=Normal）を付ける。**
Cは「これが無いと結論が出ない」項目。Cが未解決のまま納品しようとすると
ゲートB（B22）がFAILする。取得できなかった場合は、`[非公表]`・`[調査不可]`として
レポートで扱うか、重要度をNに落とす判断を明示する。

**必要証拠リスト**が本ハーネスの起点になる。「何が分かれば結論が変わるか」を先に列挙し、
そこから逆算してソースを探す。ソースを先に集めると、集まった情報に結論が引きずられる。

初期仮説は `H1, H2, ...` と採番し、各仮説に **崩壊条件**（これが観測されたら仮説は棄却）を必ず書く。

## P1: 一次情報の取得（ゲートG1）

### 手順

1. 必要証拠リストの各項目に、**どの文書のどこを見るか**を先に割り当てる（`sources.json` に `intended_use` として記録）
2. 取得を試みる。取得できた原本は `raw/` に保存し、`sources.json` に登録
3. `python3 scripts/capture_source.py <case>` でテキスト抽出とハッシュ記録
4. 取得できなかったものは障壁コードを付けて `requests/needed_sources.md` に依頼として自動追記
5. **依頼をまとめてユーザに提示**してG1を通す

### 一次情報源（日本株）

Tier1: EDINET（有価証券報告書・四半期報告書・大量保有報告書等）、TDnet 適時開示、決算短信、
株主総会招集通知、目論見書。Tier2: 決算説明資料・説明会書き起こし・統合報告書・中期経営計画・IRサイトのFAQ。
Tier3: 総務省統計局／経産省／日銀／内閣府の公的統計、業界団体統計。
Tier4: 市場データ（株価・時価総額・株価指標・信用残）。提供元とアクセス手段は案件ごとに記録する。

### 一次情報源（米国株）

Tier1: SEC EDGAR（10-K, 10-Q, 8-K, DEF 14A, S-1, 13F/13D/G, Form 4）。
Tier2: 発行体IRのearnings release / presentation / earnings call transcript / investor day資料。
Tier3: BEA・BLS・FRED・Census・各規制当局（FCC/FDA/DOE等、業種による）、業界団体統計。
Tier4: 市場データ（株価・株価指標）。提供元は案件ごとに記録する。

### 市場データ（T4）の扱い

株価・株価指標は、取得手段を問わず**他のソースと同じ手順**に乗せる。特別扱いしない。

1. 取得できた場合 — 表示されたページ本文またはCSVを `raw/` に保存し、`sources.json` に
   提供元・`retrieved_at`（**時刻まで**）・取得手段を記録してから台帳へ
2. 取得できない場合 — サイトによってはボット検知で機械取得が弾かれる。
   3回試行して駄目なら `[調査不可|FETCH_FAIL|依頼:R-xxx]` とし、基準日の終値を1行いただく形で依頼する
3. 転載・再配布を禁じているサイトがある。**調査での参照は可でも、レポートへの表の丸写しはしない**。
   必要な数値だけを台帳に取り、レポートは自分の構造で書く

**URLは記憶で書かず、必ず検索して現物に到達してから記録する。** ドメインを覚えていても
パス構造は変わる。到達できない場合はそれ自体が `FETCH_FAIL` として依頼対象になる。

### ソース登録の最小項目

`source_id / title / publisher / source_class(T1〜T6) / published_at / retrieved_at / url_or_path /
access_method(fetch|user_provided|local) / intended_use`

## P2: 台帳化（ゲートGA）

1. `raw_text/S-xxx.txt` を読み、必要証拠リストに対応する箇所を抽出して `ledger.jsonl` に書く
2. **抽出は原文コピー**。要約しながら台帳に書かない（要約は台帳の `fact` 欄で行う）
3. `python3 scripts/build_ledger.py <case>` でE-ID採番とオフセット補完
4. `python3 scripts/run_gate.py <case> --gate A` を実行し、PASSするまで直す

GAでよく出るFAILと対処:
- `QUOTE_NOT_FOUND`: 引用が原文に無い＝記憶で書いている。該当行を削除し原文から取り直す
- `SOURCE_UNUSED`: 登録したのに1件も証拠を取っていない。使わないなら `unused_reason` を書く
- `HASH_MISMATCH`: 原文が差し替わっている。台帳を作り直す

## P3: 分析・図解（ゲートGF）

- 図は `figures/F-xx.md`。データ表の各行に必ずE-ID（推定値は `[推定]` 行として分離）
- 仮説ごとに「支持する証拠 / 反する証拠 / 未検証」を並べる。**反証側を必ず探しに行く**
  （支持証拠だけを集めると、検証ではなく補強になる）
- 計算値は式と入力E-IDを残す。暗算結果を直接書かない

## P4: レポート起草（ゲートGB）

1. `assets/report_skeleton.md` を基に起草
2. `python3 scripts/run_gate.py <case> --gate B`
3. FAIL項目を潰す。**数値が照合できないときは、数値を消すか `[推定]` に落とす**（原文を探し直すのが第一選択）

## P5: 納品と改善（ゲートG5）

納品後の会話で出た指摘を `improvements/inbox.jsonl` に落とし、`improve_gate.py` にかける。
`references/self-improve.md` を参照。

## 原典再アクセス（`reverify_log.jsonl`）

**Critical項目の証拠は、収集した直後に原典へ再アクセスして検証する。**
納品直前にまとめて行わない——検証できないリンクが積み上がり、
「確認だらけ」の状態を後から一気に処理することになるため。

再アクセスの結果は3つに分岐する。

| 結果 | 判定 | 対応 |
|---|---|---|
| URLが死んでいる／開いても引用と一致する内容が無い | `hallucination` | **記述を削除**し、正しい出典を探し直す。検証台帳には記録を残す（消さない） |
| 開けるが、前後の条件で意味が反転している | `context_reversed` | 記述を修正し、**例外規定を併記**する（noteに実質的な記述で残す） |
| 単にアクセスできない | `unreachable` | `[調査不可]`として取得依頼カードを発行。**進行を止めない** |

`reverify_log.jsonl`に1行1回の再アクセスを記録する:

```json
{"eid":"E-0007","url":"https://...","reverified_at":"2026-08-25T10:05:00+09:00",
 "outcome":"match","detail":"原文と一致を確認"}
```

`outcome`は`match` / `hallucination` / `context_reversed` / `unreachable`のいずれか。

Critical項目（`scope.md`で`取得済(E-xxxx)`と記録された証拠）は、
再アクセスの記録が無ければA23がFAILする。`hallucination`判定なのに
証拠が台帳に残っていればA24、`context_reversed`なのに例外規定が
noteに反映されていなければA25がFAILする。`unreachable`はいずれも発火しない
（進行を止めない設計のため）。

収集から48時間以上経ってからの再アクセスはA26がWARNで指摘する
（「収集直後」の原則から外れている兆候として）。

## 探索ログと飽和基準（`search_log.jsonl`）

**Critical項目（`scope.md`で重要度C）**を`[未特定]`として閉じるには、
探索を尽くした裏付けを`search_log.jsonl`に残す。

1行1回の探索試行を記録する:

```json
{"item":"N-01","route":"T1","query":"有価証券報告書 セグメント別設備投資",
 "timestamp":"2026-08-01T10:00:00+09:00","new_subjects":1,"new_facts":0}
```

| フィールド | 内容 |
|---|---|
| `item` | `scope.md`必要証拠リストのID（N-01等） |
| `route` | 経路。既存のTier語彙（T1〜T6）を流用する |
| `query` | 実際に使った検索文字列 |
| `stage` | `collection`（省略時既定）または`reverify`（独立再検証） |
| `new_subjects` | この試行で新たに見つかった候補資料の数 |
| `new_facts` | この試行で新たに確認できた事実の数 |

### 飽和条件（打ち切りを許可する最低条件）

**直近3件が、経路(route)もクエリ(query)も互いに異なり、その3件全てで
新規対象・新規事実が0件であること。**

- これは最低条件であり、それ以前に新規が出ていた事実を無視するものではない
- 新規が出続ける限り、3件を超えても探索は継続する
- `[未特定|対象:N-01]`と書く際、S14がこの条件を機械検証する

### 経路の多様性が形だけになっていないか（V37/V38相当）

`python3 scripts/check_l_search_log.py <case_dir>`（または`--gate L`）が、
以下の兆候を検出する:

- **経路は分けたが、クエリが完全一致**（同じ検索の繰り返し。経路ごとに
  異なる検索語・サイト指定を使うこと）
- **独立再検証（stage:reverify）のクエリが、収集時と完全一致**
  （多様性が確保されていない）

## 分割の目安

| 状況 | 分割方法 |
|---|---|
| ソース15本超 / 証拠80件超 | テーマ別に分けて各周でGA→GB |
| 複数銘柄の比較 | 銘柄ごとに台帳を作り、比較レポートは最後に別ゲート |
| 決算またぎ | 決算前の構造理解と、決算後の実績照合を別案件にする |
| 仮説が5本超 | 優先度上位3本に絞り、残りは `[未調査]` として明示 |
