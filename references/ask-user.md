# ask-user.md — ユーザへの情報提供依頼

## 依頼を出すトリガー

以下に該当したら、推測で埋めずに依頼を出す。**推測で埋めることが最大のハルシネーション源**であり、
ユーザは数十秒でPDFを渡せることが多い。コスト比が圧倒的に依頼有利。

1. PDFに到達できない（有料/ログイン/直リンク不可/JS必須/スキャン画質）
2. 有料DB・アナリストレポート・業界専門統計が必要
3. 決算説明会の書き起こしやQ&Aなど、公開はされているが機械取得しにくい資料
4. ユーザが既に持っている可能性が高い資料（過去の分析メモ、証券会社のレポート、保有明細）
5. 取得はできたが**文字化け・表崩れ**で数値が読めない
6. 3回試行しても取得失敗（`FETCH_FAIL`）
7. 事実は取れたが**判断の前提がユーザ固有**（保有コスト、想定保有期間、リスク許容度、既存ポジションとの相関）

7番は情報ではなく前提の確認だが、これを勝手に置くと結論全体が歪むため、同じキューで扱う。

## 依頼フォーマット（`requests/needed_sources.md`）

```markdown
### R-003 [優先度:H] [状態:未提供]
- 欲しいもの: ◯◯社 2025年3月期 有価証券報告書 セグメント情報（PDFまたはテキスト）
- なぜ必要: 仮説H2「DC向け比率が利益率を規定」の検証に不可欠
- 無い場合の影響: F-01が推定のみとなり、結論の確信度が中→低に低下
- 代替案: 決算説明資料 p.12 でも可 / EDINET掲載分の該当章だけでも可
- 提供方法: PDFをチャットに添付、またはテキスト貼り付け
- 障壁コード: FETCH_FAIL（3回試行）
```

優先度の基準 — **H**: 無いと主要仮説が検証できない／**M**: 精度が落ちるが結論は出る／
**L**: 補足情報。**Hが3件を超えたら、調査スコープが大きすぎる**サインなので分割を提案する。

## 依頼の出し方

- **まとめて一度に出す。** 小出しはユーザの往復コストが高く、体感的な負荷が跳ね上がる
- 依頼と同時に、**現時点で分かっていること**を必ず先に示す。待ち時間ゼロで価値を返す
- 「無い場合の影響」を書く。ユーザが提供コストと価値を天秤にかけられるようにするため
- 提供されない選択も尊重する。その場合は該当箇所を `[調査不可|依頼:R-003|ユーザ判断で見送り]` として進める

## 提供を受けた後の処理

1. `raw/` に保存（ファイル名は `S-0xx_<簡潔な説明>.<ext>`）
2. `sources.json` に登録。`access_method:"user_provided"`, `provided_at`, `provided_by:"user"`
3. `capture_source.py` を実行してテキスト抽出とハッシュ記録
4. `requests/needed_sources.md` の該当依頼を `[状態:提供済み|S-012]` に更新
5. **提供資料も同じ検証を通す。** ユーザ提供だからといって台帳とチェックAを省略しない
   （貼り付け時の欠落や、別期の資料が混ざる事故が実際に起きる）

## 依頼してはいけないもの

- 一般公開されていて自力で取得できる資料（依頼する前に3回試行）
- 個人的な機微情報（口座残高の詳細等）。判断に必要なら「比率」「レンジ」で足りるか先に検討する
- インサイダー情報に該当しうる未公表の内部情報。これは**受け取らない**。
  受け取ってしまった場合はレポートに使わず、その旨を伝える
