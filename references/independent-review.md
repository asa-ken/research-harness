# independent-review.md — 独立レビュー（GC）

## なぜ必要か

チェックA・Bは強力だが、**同じClaudeが台帳とレポートの両方を書いている**。
台帳を書く段階で入った誤り（読み違え、主語の取り違え、引用と逆向きの解釈）は、
両方のチェックを素通りする。二重チェックに見えて、実際には同一著者による自己整合性の確認でしかない。

機械化できる部分は A15/A16（単位・期）、B13（否定の向き）、B14（変化の主張）で塞いだが、
**「引用は本物だが、その引用はその主張を支持していない」**という逸脱は、
意味の判断を要するため原理的に機械では判定できない。

そこで最後に、**書いた者以外**が主張と引用を突き合わせる工程を置く。

## 手順（P4の後、納品前）


```bash
python3 scripts/extract_claims.py <case_dir>     # checks/claims_review.md を生成
```

生成された表は「主張／根拠E-ID／引用原文」の対で並んでいる。
これを、次のいずれかの方法で判定する。

| 方法 | 独立性 | 手間 | 費用 |
|---|---|---|---|
| **A. Cowork / Claude Code のサブエージェントに判定させる** | 中〜高 | **低（自動）** | プラン利用量のみ |
| **B. 新しいチャットに貼って判定させる** | 中〜高 | 中（手動） | プラン利用量のみ |
| **C. ユーザ自身が読む** | 高 | 中 | なし |
| **D. 同一セッションのClaudeが自己点検** | **低（推奨しない）** | 低 | なし |

API経由の自動判定は、意図しないクレジット消費を避けるため実装していない
（スクリプトは一切ネットワークに接続しない）。A・Bはサブスクリプション側で完結する。

**Dを推奨しない理由**: 台帳とレポートを書いた文脈がそのまま残っているため、
書いたときの理解をなぞることになる。誤りを見つけるべき側が、誤りを作った側の記憶を持っている。
（これは構造からの推論であり、定量的に検証したものではない）

### 方法A: サブエージェントによる自動化（推奨）

Cowork / Claude Code はサブエージェントを独立したコンテキストウィンドウで動かせる。
親セッションの文脈を持たないため、手で別チャットに貼るのと同等の分離が自動で得られる。

親セッションでの依頼例:

```
サブエージェントを1つ起動し、次の作業だけをさせてください。
渡すファイル: <case>/checks/claims_review.md と <case>/raw_text/ 配下

指示:
「表の各行について、引用文が主張を支持しているかを判定する。
 支持 / 部分的 / 不支持 / 判断不能 のいずれかを付け、不支持・部分的は理由を書く。
 一般常識や業界知識で補って支持としない。引用に書かれていないことは書かれていないと扱う。
 必要なら raw_text の原文を確認してよい。」

結果を claims_review.md の判定列に書き戻してください。
```

**渡してよいのはファイルパスと判定基準だけ。** レポート本文や、
これまでの調査経緯・結論の要約を指示文に混ぜない。コンテキストは分離されていても、
**親が渡す指示文から意図が漏れれば汚染される**。ここが自動化の成否を分ける。

主張が多い場合は行を分割して複数のサブエージェントに並列で振ってよい。
ただし各サブエージェントの利用量は独立して積み上がるので、件数と消費のバランスは見ること。

### 方法Bの渡し方

Aの独立性が「中〜高」なのは、レポートを書いた文脈を持たない別インスタンスであれば、
書き手の意図に引きずられずに引用文だけを読めるため。ただし同じモデルなので、
同種の読み違いを繰り返す可能性は残る。**結論に効く主張はBで確認するのが安全**。

### 方法Aの渡し方

新しいチャットを開き、`claims_review.md` と `raw_text/` を貼って、こう頼む
（依頼文は `claims_review.md` の末尾にも出力される）:

> この表の各行について、引用文が主張を支持しているかを判定してください。
> レポート全体の文脈や、書き手の意図は考慮しないでください。
> 引用文だけを読んで、支持 / 不支持 / 部分的 / 判断不能 のいずれかを付け、
> 不支持・部分的の場合は理由を書いてください。原文に戻って確認してもかまいません。

**「このレポートは正しいですか」と聞かない。** 全体の妥当性を問うと、
もっともらしさで判断されてしまう。1行ずつの照合に限定するのが要点。これはA・B共通。

## 着眼点

- 主語・対象が入れ替わっていないか（別セグメント、別会社、別製品、連結/単体）
- 主張の向きが引用と逆になっていないか
- 単一時点の引用で、変化や傾向を語っていないか
- 会社予想・第三者見解を、事実として書いていないか
- 引用の一部だけを切り出し、条件や留保を落としていないか

## 判定後

**不支持・部分的が1件でもあれば、レポートを修正してゲートBからやり直す。**
判断不能は、引用が主張に対して弱いということなので、証拠を取り直すか主張を弱める。

結果は `checks/claims_review.md` に残し、修正内容を `improvements/inbox.jsonl` にも起票する。
同じ種類の読み違いが2案件で起きたら、汎用性ゲートを通して機械チェック化を検討する。

## この工程を省いてよい場合

- 調査深度が「サマリ」で、結論が投資判断に直結しない
- 主張が10件未満で、ユーザ自身がすべての引用を読める

**深掘り調査では省かない。** 省くなら、レポートの「本調査の限界」に
独立レビュー未実施であることを明記する。
