# checker.md — Wチェックの仕様

チェッカーの原則: **Claudeは判定しない。スクリプトの出力だけが判定である。**
「確認しました」「整合しています」という自己申告は証拠にならないため、ゲートの合否には使わない。

## チェックA: ソース ⇔ 記録一覧（`check_a_source_ledger.py`）

台帳の各証拠が本当に原文に存在するかを、文字列一致で検証する。

| コード | 種別 | 検査内容 |
|---|---|---|
| `A01 ANCHOR_NOT_FOUND` | FAIL | 識別語が原文に無い／範囲を特定できない／識別語が40字超 |
| `A02 ANCHOR_AMBIGUOUS` | WARN | 識別語が複数箇所に一致し範囲を一意に決められない |
| `A03 OFFSET_CONFLICT` | FAIL | 記録された位置と識別語から解決した位置が一致しない |
| `A04 SOURCE_MISSING` | FAIL | `source_id` が `sources.json` に無い／`raw_text` が無い |
| `A05 HASH_MISMATCH` | FAIL | 抽出テキストのSHA256が `sources.json` の記録と不一致（原文差し替え） |
| `A06 SOURCE_UNUSED` | WARN | 登録ソースから証拠が1件も無く `unused_reason` も無い（**逆方向の網羅性**） |
| `A07 SCHEMA_ERROR` | FAIL | 必須フィールド欠落・型不正・`eid` 重複 |
| `A08 VALUE_NOT_IN_QUOTE` | FAIL | `value.number` に相当する数字が `quote` 内に見当たらない |
| `A09 TIER_CONFIDENCE` | WARN | T5/T6ソースなのに `confidence:高` |
| `A15 UNIT_UNSUPPORTED` | FAIL | `value.unit` が引用中に無く裏付けられない（単位の取り違え＝桁違いの誤り） |
| `A16 PERIOD_UNSUPPORTED` | FAIL/WARN | `value.period` が `period_context`・引用と食い違う（相対表現・会社予想はWARN） |
| `A17 SOURCE_TIER_MISMATCH` | FAIL/WARN | 調査項目に対してソース種別が不適切（実績値をT3以下で取る＝FAIL、市場規模を発行体資料T2で取る＝WARN） |
| `A18 QUOTE_CONTEXT` | WARN | 引用の切り出し範囲の問題（文の途中で切っている／直前直後の留保・条件を落としている／ページ境界をまたぐ） |
| `A19 PREMISE_ELSEWHERE` | WARN | 文書冒頭側に前提条件の記載があるが、引用は離れた位置（後半）にある |
| `A20 SCOPE_MISMATCH` | FAIL/WARN | `value.basis_scope`（連結/単体・累計/単四半期）が引用と矛盾（FAIL）または確認できない（WARN） |
| `A21 GRANULARITY_UNCLEAR` | WARN | 複数期が並ぶ引用（要約表由来の疑い）でconfidenceが高いまま |
| `A27 CONTEXT_PAGEWIDE` | WARN | 引用と同じページ範囲（PDFは当該＋次ページ／WEBはソース全体）に留保・条件語があり、引用にもnoteにも反映されていない。A18(前後100字)とA19(冒頭)の中間を埋める |
| `A11 NO_BASIS_DATETIME` | FAIL | 株価・株価指標（T4またはタグ`財務.株価指標`）に `basis_datetime`（時刻まで）が無い |
| `A12 METRIC_BASIS_UNCLEAR` | FAIL | PER/PBR/利回り等で、noteに基準（コンセンサス予想/実績）と対象期が無い。会社予想ベースは採用基準外としてFAIL |
| `A13 NOT_CLOSE_PRICE` | FAIL | 株価が終値ベースでない（noteに終値の記載が無い／引け時刻前のbasis_datetime／取得日より後の日付） |
| `A14 NON_TRADING_DAY` | WARN | basis_datetimeが土日。祝日・半日立会は判定できないため自分で確認する |
| `A10 STALE_BASIS` | WARN | `basis_date` が調査基準日より18ヶ月以上前（陳腐化） |

A08が本チェックの要。「引用は本物だが数字だけ違う」という最も見つけにくい誤りを潰す。
A11・A12はバリュエーション記述に固有の事故（分子と分母の時点・定義がずれたまま「割安」と書く）を防ぐ。

## チェックB: 記録一覧 ⇔ レポート（`check_b_ledger_report.py`）

レポートの記述が台帳に還元できるかを検証する。**両方向**を見る。

| コード | 種別 | 検査内容 |
|---|---|---|
| `B01 EID_UNRESOLVED` | FAIL | レポートの `[E-xxxx]` が台帳に無い |
| `B02 UNSOURCED_CLAIM` | FAIL | 数値・固有名詞・断定を含む文にE-ID/推定/ステータス表記が無い |
| `B03 NUMBER_MISMATCH` | FAIL | 文中の数値が、引用したE-IDの `quote`/`value` に見当たらない |
| `B04 CALC_MISMATCH` | FAIL | `[計算:...]` の再計算結果と本文の値がずれる（許容誤差既定0.5%） |
| `B05 INFER_INCOMPLETE` | FAIL | `[推定]` に根拠E-ID・確信度・反証条件のいずれかが欠落 |
| `B06 FIGURE_UNSOURCED` | FAIL | `figures/` のデータ表にE-IDが無い行がある（`[推定]`行を除く） |
| `B07 ORPHAN_EVIDENCE` | WARN | 台帳にあるがレポートでも図でも一度も使われていない証拠（**取りこぼし**） |
| `B08 TAG_GAP` | WARN | 調査カテゴリ10区分のうち、証拠もステータス記述も無い章がある |
| `B09 FORECAST_AS_FACT` | FAIL | `claim_type:forecast` のE-IDを、会社予想と明示せず断定文で使用 |
| `B10 QUOTE_TOO_LONG` | WARN | レポート中の直接引用が長すぎる／同一ソースから複数回引用 |

B07は「調べたのに書き忘れた」を拾う。B02は「調べていないのに書いた」を拾う。
この2つで**両方向の欠落**が閉じる。

| `B13 NEGATION_MISMATCH` | FAIL | 否定の主張だが、引用側に否定の裏付けが無い |
| `B14 NO_COMPARISON_BASE` | FAIL | 変化・比較の主張だが、証拠が1時点しかない |
| `B19 SUBJECT_MISMATCH` | FAIL | 台帳の`subject`と、レポートで使われている別の`subject`が混同されている（統制語彙による高精度判定） |
| `S13 GHOST_EVIDENCE` | FAIL | `[非公表]`の確認E-IDが台帳(ledger.jsonl)に実在しない（架空のIDでの回避を防ぐ） |
| `C05 RUBBER_STAMP_SUSPECT` | WARN | GC判定が5件以上あり、全件『支持』（実質的な吟味が無かった兆候の可能性） |
| `C06 DUPLICATE_COMMENT` | WARN | GCコメントの60%以上が同一文言（コピー&ペーストの兆候の可能性） |
| `B20 BULK_CATEGORY_SKIP` | WARN | 複数カテゴリを1つの理由で一括スキップしている（個別の吟味が無い兆候） |
| `B21 SUPERLATIVE_UNSUPPORTED` | FAIL | 最上級・排他の主張（唯一・最大・首位等）に、順位・シェア等の根拠が引用に無い |
| `B22 CRITICAL_EVIDENCE_MISSING` | FAIL | `scope.md`の必要証拠リストで重要度Cの項目が未解決のまま |
| `B18 QUESTION_UNANSWERED` | WARN | `scope.md` で採用した問いが、レポートでも図でも扱われていない |
| `B15 FIGURE_SET` | FAIL/WARN | 最小図解セット（F-01〜F-04必須、F-05推奨）が欠けている |
| `B16 TERM_ELSEWHERE` | WARN | 主張中の語が引用に無く、原文の**別の箇所**に存在する（引用の取り違えの疑い） |
| `B17 SUBJECT_MISMATCH` | WARN | 主張にしかない語と引用にしかない語が同時にある（対象のすり替えの疑い） |

B13〜B17は「引用は本物だが主張が引用と噛み合っていない」逸脱を、形の上で捕らえる試み。

- **B16は精度が高い**。「その語は原文のどこかにあるのに、引用した箇所には無い」という
  非対称性を見るため、パラフレーズによる誤検出が起きにくい
- **B17は再現率が高い代わりに精度が低い**（検証では正常ケースにも約半分の割合で反応した）。
  誤りの断定ではなく確認の促しとして扱い、FAILにしていないのはこのため

文脈の判定そのものは形では閉じない。残りは2層で扱う:

| 層 | 手段 | 精度 | 独立性 |
|---|---|---|---|
| 1 | B13〜B17（決定論的・自動） | 中〜低 | 高（機械） |
| 2 | GC 独立レビュー（別セッション／人） | 高 | 高 |

層2は `extract_claims.py` が作る表を新しいチャットに貼るだけで実施できる。
外部APIは使わない（意図しない課金を避けるため、その経路自体を持たせていない）。
詳細は `references/independent-review.md`。

### A17: ソース選択の妥当性

「何を調べているか」に対して「どの種別のソースを使ったか」を照合する。
台帳のタグごとに、根拠として認めるTierを定めている。

| タグ | 認めるTier | 判定 | 理由 |
|---|---|---|---|
| 財務.実績 / 財務.健全性 | T1, T2 | FAIL | 実績値は法定開示か発行体一次資料で取る |
| 市場環境 / 競争環境 | T1, T3, T4 | WARN | 市場規模・シェアを発行体の自称に依存させない |
| 財務.株価指標 | T4, T1 | WARN | 株価指標は市場データから取る |

やむを得ず範囲外のソースを使う場合は、`note` に**出所と限界**を書けば通る
（「出所は会社推計。第三者統計に代替なし」など）。黙って使うことだけを止めている。

### A18: 引用の切り出し範囲（文脈の検査範囲）

引用が原文に存在しても、**直前直後の留保を落として切り出せば意味は変わる**。
そこで引用位置の前後100字を窓として見る。

- 文末で終わっていない／文頭から始まっていない → 条件節や結論部を落とした疑い
- 窓の中に留保・条件語（ただし・除く・遡及・組替・一過性・暫定 等）があり、
  引用がそれを含んでいない → 切り取りの疑い
- 引用がページ境界（`<<<PAGE n>>>`）をまたいでいる → ヘッダ・フッタ混入の疑い

**「なお」「一方」のような弱い接続詞は対象外にしている。** 開示文書で頻出するため、
入れると警告が飽和して読まれなくなる（実測で誤検出が支配的だった）。

**A18は前後100字しか見ない。** 局所的な切り取りは検出できるが、
『前提は冒頭、根拠は後半』という開示文書によくある配置は、局所窓では捉えられない。

### A19: 文書全体の前提ゾーン検査

A18を補う形で、**文書全体**を対象にした検査を別途行う。

1. 文書の冒頭側（先頭15%、500〜2000字の範囲）を「前提ゾーン」とみなす
2. 前提ゾーンに「算定の基礎」「前提条件」等の見出し語があるか探す
3. 引用位置が前提ゾーンより後ろにあり、`note` に前提を確認した旨の記載が無ければ WARN

引用自体が前提ゾーン内にある場合や、文書に前提条件の記載が無い場合は発火しない。
実測では、前提記載のない7,000字超の長文でも誤検出は0件だった。

それでも**文書全体の意味的な整合はここでは閉じない**。見出し語に依存した検出なので、
前提条件が別の書き方（「なお、本資料の数値は次の条件による」等、定型外の表現）で
書かれている場合は素通りする。最終的な読解範囲の担保は
`references/evidence.md` の運用ルールとGCに依る。

### 「文脈」の分解と実装状況

文脈チェックは場当たり的に追加されてきたため、何を検査していて何を検査していないかを
一度分解して整理する。

| 次元 | 意味 | 実装 |
|---|---|---|
| 時間 | いつの時点の情報か | A16（期）、A11/A13/A14（株価時点） |
| 条件・前提 | どんな仮定の下で成り立つか | A18（局所）、A19（文書全体） |
| 極性・向き | 肯定/否定が引用と一致しているか | B13 |
| 比較基準 | 変化を語るなら比較対象は確立しているか | B14 |
| 単位・尺度 | 数値の単位は引用と一致するか | A15 |
| 修辞的完全性 | 文の途中で切っていないか | A18 |
| **主体の同一性** | 主張の主語（セグメント/会社/連結・単体）と引用の主語が同じか | A20（連結/単体・累計/単四半期）、B19（セグメント名等、opt-in）、B16/B17（自由語彙、低〜中精度） |
| **粒度・集計** | 単一原資料の値か、複数期をまとめた要約表の値か | A21 |

主体の同一性のうち、**連結/単体・累計/単四半期はA20が機械的に閉じる**（`value.basis_scope`を
指定すれば）。**セグメント名の取り違えはB19が統制語彙（`subject`フィールド）で検出する**が、
`subject`を書かなければ発火しない。空欄のまま運用すると、この次元はB16/B17の低精度な
自由語彙検出だけに戻る。**セグメント別の証拠を登録するときは`subject`を書く習慣を付けること。**

### A20: 連結/単体・累計/単四半期の一致

`value.basis_scope` に「連結」「単体」「累計」「単四半期」等を書くと、引用中の該当語と
照合する。引用に**反対の区分が明示**されていれば矛盾としてFAIL、区分の記載自体が
引用に無ければ確認できないとしてWARNに留める（開示文書は文書全体の適用範囲を
冒頭でのみ宣言し、個々の文には書かないことが多いため）。

### A21: 複数期の要約表からの引用

引用中に異なる期を示す語（`25年3月期`等）が2つ以上あれば、複数期をまとめた
比較表からの抜粋である可能性が高いと判断する。`evidence.md`の運用ルール
（要約表からの引用はconfidenceを1段下げ、noteに明記する）が実際に守られているかを、
このコードで検証する。noteに「要約表」「ファクトシート」等の語があれば通る。

### B19: 主体（subject）の一致

台帳の`subject`フィールドは著者が明記する統制語彙で、B16/B17の自由語彙推測より
精度が高い。証拠の`subject`と異なる、**別の証拠が使っているsubject**が主張に
含まれていれば、取り違えとしてFAIL。`subject`が空の証拠には適用されない。

## A23〜A26: 原典再アクセス（収集直後の検証）

`references/workflow.md`「原典再アクセス」参照。Critical項目の証拠は
収集直後に再アクセスして検証する設計で、これを`reverify_log.jsonl`という
検証台帳で裏付ける。

| コード | 種別 | 検査内容 |
|---|---|---|
| `A22 TAMPER_FLAG` | FAIL | `capture_source.py`が検出した改竄フラグ（原本差し替え・raw_text編集）が未解消 |
| `A23 REVERIFY_MISSING` | FAIL | Critical項目の証拠に再アクセス記録が無い |
| `A24 HALLUCINATION_NOT_REMOVED` | FAIL | `hallucination`判定なのに証拠が台帳に残っている |
| `A25 CONTEXT_REVERSAL_UNCORRECTED` | FAIL | `context_reversed`判定なのに例外規定がnoteに反映されていない |
| `A26 REVERIFY_DELAYED` | WARN | 収集から48時間以上経ってからの再アクセス（「収集直後」の原則から外れる兆候） |
| `A28 REVERIFY_USED_MISSING` | FAIL | レポートで実際に引用した証拠に原典再アクセスの記録が無い。重要度Cの予測に頼らず、結論が実際に依存した証拠(referenced)全てに再アクセスを要求する。`checks/exceptions.md`にE-IDと理由(10字以上)を書けば個別解除 |
| `A29 REVERIFY_USED_UNREACHABLE` | WARN | レポートで使った証拠が`unreachable`のまま。代替ソースを探すか本文に限界を明記。exceptions.mdで解除可 |

`unreachable`はいずれの検査も発火しない。**アクセスできないこと自体は
`[調査不可]`として扱い、進行を止めない設計のため。**

## S14: 飽和条件の機械検証

`[未特定]`は「探索ログに裏付けが無ければ書けない」ようにしてある。
`references/workflow.md`「探索ログと飽和基準」参照。

## ゲートL: 探索ログの多様性（V37/V38相当）

`check_l_search_log.py`。S14が個々の`[未特定]`宣言時に検証するのに対し、
こちらは探索ログ全体を走査して「経路を分けたつもりが実質同じ検索だった」
という兆候を早期に発見する。

| コード | 種別 | 検査内容 |
|---|---|---|
| `L00 EMPTY_LOG` | WARN | 探索ログが空 |
| `L01 SAME_QUERY_DIFF_ROUTE` | WARN | 同一項目内で、経路が異なるのにクエリが完全一致 |
| `L02 REVERIFY_QUERY_DUP` | FAIL | 独立再検証のクエリが収集時と完全一致 |

L02は`stage:reverify`のログが無ければ発火しない。独立再検証（原典再アクセス）の
運用フローは未確定のため、現状は将来の拡張に対する予約的な検査。

## ステータスLint（`lint_status.py`）

使用可能なトークンは `[非公表] [未調査] [調査不可] [推定] [未特定]` の5つのみ。
各トークンの成立条件は `references/status.md` で定義する。

| コード | 種別 | 検査内容 |
|---|---|---|
| `S01 NO_CONFIRM_EID` | FAIL | `[非公表]`に確認証拠E-IDが無い |
| `S02 NO_ALTERNATIVE` | WARN | `[非公表]`に代替アプローチが無い／短すぎる |
| `S03 NO_NEXT_ACTION` | FAIL/WARN | `[未調査]`に次アクションが無い（FAIL）／4字未満で具体性が無い（WARN） |
| `S04 NO_PRIORITY` | FAIL | `[未調査]`に優先度(H/M/L)が無い |
| `S05 NO_BARRIER_CODE` | FAIL | `[調査不可]`に障壁コードが無い |
| `S06 NO_REQUEST_ID` | FAIL | `[調査不可]`に依頼ID(R-xxx)が無い |
| `S07 NO_BASIS_EID` | FAIL | `[推定]`に根拠E-IDが無い |
| `S08 NO_CONFIDENCE` | FAIL | `[推定]`に確信度が無い |
| `S09 NO_COUNTEREVIDENCE` | FAIL | `[推定]`に反証条件が無い |
| `S10 VAGUE_WORD` | FAIL | 「不明」「判然としない」等の素の曖昧語（5分類に置き換える） |
| `S11 UNKNOWN_REQUEST_ID` | FAIL | 依頼IDが`requests/needed_sources.md`に存在しない |
| `S12 NOT_NEGATIVE_EVIDENCE` | FAIL | `[非公表]`の確認証拠が`claim_type:negative`でない |
| `S13 GHOST_EVIDENCE` | FAIL | `[非公表]`の確認E-IDが台帳に実在しない（架空IDでの回避を防ぐ） |
| `S14 NOT_SATURATED` | FAIL | `[未特定]`に項目IDが無い、または探索ログの飽和条件を満たさない |

## ゲート合否

- **FAILが1件でもあれば不合格。** 次フェーズに進まない
- WARNは合格だが、ゲートレポートに残り、レポート冒頭の「本調査の限界」に反映する
- 例外を通す場合は `checks/exceptions.md` に **コード・対象・理由・承認者(ユーザ)** を書く。
  Claude単独で例外を作らない（自己申告での通過を許すと機構が形骸化する）

## B21: 最上級・排他の主張（既存機構の穴埋め）

「唯一・最大・首位」といった語彙は以前からASSERTION_WORDSに存在したが、
**用途はB02（無出典文の検出）のみ**だった。つまり出典さえ付いていれば、
最上級の主張は無検証で通っていた。

最上級は、個別の数値ではなく**比較対象の全体を調べたこと**を前提とする主張である。
自社の売上高が書かれた引用は、それが業界最大であることの根拠にならない。

B21は、最上級語を含む主張について、引用側に順位・シェア・ランキング等の
根拠表現があるかを確認する。無ければFAIL。逃げ道は2つ:
第三者統計(T3)で裏を取るか、`[推定|根拠:...|確信度:...|反証:...]`に落とす。

## B22: 必要証拠リストの充足（実在した穴）

`scope.md`の必要証拠リストは、**これまでどのスクリプトからも検証されていなかった**。
結論を左右する項目が未取得のままでも、ゲートBは通過していた。

必要証拠リストに**重要度列（C=Critical / N=Normal）**を追加し、
Critical項目が未解決（E-IDも無く、非公表・調査不可の判断も無い）のまま
残っていればFAILにする。

解決方法は3つ: 取得してE-IDを記録する / `[非公表]`・`[調査不可]`として
レポート本文で扱う / 重要度をNに落とす判断を明示する。
**「調べなかったので空欄」という状態を、そのまま納品できないようにする。**

## 実データ検証で判明した設計上の前提誤り（重要）

フィクスチャだけで開発していた期間に蓄積した、**実際の開示文書では成立しない前提**を
記録する。実データ（TDnet適時開示の決算短信）を1件通した結果、以下が判明した。

| # | 誤った前提 | 実際 | 対応 |
|---|---|---|---|
| 1 | 単位は引用文字列の中にある | **表ヘッダに1度だけ**書かれ、各行には無い | A15: 原文の引用位置より手前1500字も探索 |
| 2 | 連結/単体の区分も引用内にある | 同じく表ヘッダ・文書冒頭で1度だけ宣言 | A20: 同上 |
| 3 | 引用は文（句点）で終わる | **表形式データは句点で終わらない** | A18: 表形式パターンを検出して除外 |
| 4 | 主張には必ず出典が付けられる | メタ情報・解釈文・仮説表・付録は出典を持ち得ない | B02: 4類型を例外化（後述） |
| 5 | 主張と引用は語彙が一致する | 「売上債権」vs「受取手形、売掛金及び契約資産」のように**科目名と略称が異なる**のが通例 | B16/B17: STOPWORDS拡充、表形式引用を除外 |

**#4の例外4類型**（これらをFAILにするとレポートが書けなくなる）:

1. 冒頭のメタ情報行（調査基準日・使用ソース等）
2. 同一節内で根拠が既に示された後の解釈・含意の文（「ただし」「つまり」等で始まる）
3. 仮説表・ソース一覧のように、セル内にE-IDを列挙する表
4. 「本調査の限界」「付録」節の記述

根拠の文脈は**段落（節）単位で継続**する。節が変われば文脈は切れ、
新たな数値を持ち出す文も独立した主張として扱う。

### 教訓

自作フィクスチャは、作った本人の思い込みをそのまま再現するため、
**前提の誤りを検出できない**。実データを1件通すだけで、
142件のテストが素通りさせていた欠陥が5件見つかった。
チェック機構を追加・変更したら、実際の開示文書で1件通すこと。

## 性悪説での再監査（このリリースで修正した6件）

「ルールの文言は満たすが、実質は手抜きできる」経路を洗い出した結果を記録する。
1件は、Skill自身のサンプルケースで実際に使われていた手口だった。

| # | 抜け穴 | 深刻度 | 修正 |
|---|---|---|---|
| 1 | `<!-- no-check -->`ブロックで、任意の主張を**全チェックから丸ごと隠せた** | **重大** | 機構自体を廃止 |
| 2 | `[非公表\|確認:E-9999]`のように**存在しないE-IDを書けば**S01もS12も素通りしていた | **重大** | S13を新設し、台帳に無いE-IDをFAILにする |
| 3 | A15/A16/A17/A19/A21が、`note`に**キーワード1語書くだけ**で黙った（例: note="期"） | 高 | `substantive_ack`で15字以上の実質的な記述を要求 |
| 4 | `[未調査\|次:確認]`のような**空虚な次アクション**がS03を素通りしていた | 中 | 4字未満の次アクションはWARN |
| 5 | Gate Cは判定欄が埋まっていれば通るため、**全件「支持」を機械的に書くだけ**でも通った | 中（未解決） | C05/C06で兆候を検出（下記） |
| 6 | `case_terms.txt`が空欄のまま放置されがちで、汎用性ゲートT1の効きが弱かった | 低 | `init_case.py`が対象企業名を自動シード |

### #1（no-checkブロック）について

過去に「証跡コメント等のメタ情報を除外する」という名目で実装したが、
実際には**任意の複数行を検査から丸ごと除外できる汎用のバイパス**になっていた。
正当な用途（証跡コメントの除外）は単一行HTMLコメントの除外だけで十分満たせるため、
複数行ブロック機構は**廃止**した。「除外機能」自体を持たないことが、
最も確実な対策である。

### #5（Gate Cのラバースタンプ）について、正直な限界

C05/C06は「全件が支持」「コメントが使い回し」という**統計的な兆候**を検出するが、
これは**確定的な検証ではない**。本当に全件が正当に支持される調査もあり得るし、
逆に、多様なコメントを書きながら実質は読んでいない、ということも起こり得る。

**Gate Cが検証しているのは「判定欄が埋まったという形式」であって、
「独立した視点で実際に吟味したという実質」ではない。** これは自己申告制の
仕組みである以上、機械的には閉じられない。最終的な保証は、
`references/independent-review.md`が推奨する「別セッション・別人による実施」
という運用そのものに依存する。

## Wチェック結果の集約とExcel出力（C-1/C-2/C-3）

`export_wcheck.py`が、証拠ごとのC-1/C-2/C-3相当の判定結果を集約し、


### 対応関係と判定の出所

| 項目 | 何を見るか | 判定の出所 |
|---|---|---|
| C-1（記述→原文整合） | GCの判定結果 | `checks/claims_review.md`の判定列 |
| C-2（原文→原典整合） | 原典再アクセスの結果 | `reverify_log.jsonl`のoutcome |
| C-3（文脈整合） | A15/A16/A18/A19/A20/A21/A27の直近実行結果 | `check_a_source_ledger.py`を再実行して取得 |

### 設計原則: 状態は固定語彙、理由は機械生成のみ

判定は「問題なし／懸念あり／問題あり／未実施」の4値のみ。**Claudeが自由記述で
書き込む欄は無い。** 理由文も、各チェックが実際に出力したメッセージをそのまま
転記したものであり、この場で新たに作文しない。

これは意図的な設計判断である。自由記述を許すと、詳細な理由文ほど
「もっともらしく見える」ため、中身の伴わない記述で検証をすり抜けられる
（性悪説監査で見つけた`note`欄の抜け穴と同型の危険）。固定語彙＋機械生成の
理由文に限定することで、この経路自体を塞いでいる。

### C-1/C-2とC-3の非対称性（正直な限界）

C-3は完全に機械のみで判定・理由文とも生成される。C-1・C-2は判定こそ固定語彙だが、
**理由文（GCのコメント、原典再アクセス時の確認メモ）は、その検証行為を行った者が
その場で記録したもの**である。これは台帳の自己申告とは異なる
（GCは別セッション/別人での実施が前提、原典再アクセスは実際の再取得を伴う）が、
完全な機械生成ではないことは明記しておく。

## ゲートC: 独立レビュー(GC)の実施確認

以前はGCが「文章上の指示」でしかなく、実施したかを確認するゲートが存在しなかった。
`extract_claims.py`が表を作っても、判定列を埋めずに納品することを誰も止められなかった。

`check_c_claims_review.py`がこれを埋める。

| コード | 種別 | 検査内容 |
|---|---|---|
| `C00 NOT_REVIEWED` | FAIL/WARN | claims_review.mdが未生成。対象5件以上でFAIL、5件未満はWARN |
| `C01 UNJUDGED_ROW` | FAIL | 判定列が空欄の行がある |
| `C02 UNRESOLVED_FINDING` | FAIL | 不支持・部分的の判定が残っている |
| `C03 WEAK_EVIDENCE` | WARN | 判断不能の判定がある（証拠が主張に対して弱い） |
| `C04 STALE_TABLE` | WARN | 表の行数が現在のレポートの主張数より少ない（再抽出漏れの疑い） |

```bash
python3 scripts/run_gate.py <case_dir> --gate C
```

C02が残っている限りゲートCはFAILする。**レポートを修正 → ゲートBをやり直す →
claims_review.mdを更新 → ゲートCを再実行**、という順で解消する。

## カテゴリ一括スキップの可視化（B20）

B08は「カテゴリ名の直後200字にステータス表記があるか」しか見ないため、
複数カテゴリ名を並べて末尾に1個の理由を書けば、個別の吟味なしに一括で

B08が見逃す「形式は満たすが実質が薄い」ケースを可視化する追加チェック。

## severity自己申告の検証（改善ゲート T6）

`improve_gate.py`の`severity:"correctness"`は、本来「誤情報がレポートに載った」
種類の欠陥にのみ与えられ、再発を待たず即PROMOTEされる特権を持つ。しかし
severityは自己申告であり、検証する仕組みが無かった。T6テストは
`observation`/`failure_mode`に誤りを示す語（誤り・誤検出・矛盾・取り違え等）が
無いのにcorrectnessを名乗るケースを検出し、**即時昇格の特権だけを剥奪**する
（REJECTはしない。通常の再発待ちルートに戻すだけ）。これは弱いヒューリスティックで、
意味理解を要する完全な検証ではない。最終的にはdecision_log.mdを人が確認すること。

## 実行証跡

`run_gate.py` は実行のたびに `checks/receipt_<gate>.json` を書く。
対象ファイル（report.md / ledger.jsonl / sources.json）のハッシュを含むため、
**ゲート後にレポートを書き換えると検出できる**。

PASS時に表示される `<!-- gate:B PASS receipt=... -->` をレポート冒頭に貼り、
受け取った側は `verify_gate.py` で「本当に実行されたか」「その後改変されていないか」を確認する。

## 実行

```bash
python3 scripts/run_gate.py <case_dir> --gate A    # P2完了時
python3 scripts/run_gate.py <case_dir> --gate B    # P4完了時
python3 scripts/run_gate.py <case_dir> --gate all
```
結果は `checks/gate_<X>_<timestamp>.md` に保存され、終了コードが 0=PASS / 1=FAIL。
