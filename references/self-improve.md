# self-improve.md — 自己改善と汎用性ゲート

## 何を拾うか

納品後の会話には、ハーネスの欠陥が現れる。以下のシグナルを検出したら改善候補を起票する。

| シグナル | 例 | 疑うべき欠陥 |
|---|---|---|
| 出典への疑義 | 「その数字どこから？」 | 引用・E-ID運用の不備 |
| 観点の欠落指摘 | 「顧客集中度は見た？」 | 必要証拠リストの雛形が不足 |
| 誤りの指摘 | 「その期の値は違う」 | チェック項目の穴（最優先） |
| 手戻り | 同じ資料を2回探した | ソース探索順序の非効率 |
| 読みにくさ | 「結論が分からない」 | レポート構成の問題 |
| ユーザによる手直し | 出力を書き換えて使った | 暗黙の期待とテンプレのズレ |
| 依頼の空振り | 提供依頼が的外れだった | 依頼トリガーの誤り |

**起票は判断を伴わない。** 拾えるものは全部 `improvements/inbox.jsonl` に入れる。
選別はゲートの仕事であり、起票段階で絞ると、後で「なぜ直さなかったか」が残らない。

## 改善候補の形式（`improvements/inbox.jsonl`）

```json
{"id":"I-004","raised_at":"2026-08-22","case":"case1",
 "signal":"誤りの指摘",
 "observation":"四半期売上を前年同期でなく前四半期と比較していた",
 "failure_mode":"季節性のある事業で比較基準を明示していなかった",
 "proposal":"時系列比較を書く際は比較基準(YoY/QoQ)を必ず明記し、季節性の有無を確認する",
 "target_file":"references/diagrams.md",
 "scope_evidence":["半導体製造装置(日本株)でも小売(米国株)でも同じ誤りが起きうる"],
 "recurrence":1}
```

## 汎用性ゲート（`scripts/improve_gate.py`）

「その調査に最適化された改善」は、次の調査で**害になる**。
（例:「必ずデータセンター需要に言及する」というルールは、内需小売の調査では雑音になる）
そのため昇格前に5テストを通す。

| テスト | 判定 | 不合格時 |
|---|---|---|
| **T1 固有名詞** | proposal に特定銘柄・ティッカー・特定企業名・特定年月が含まれないか | 一般化して再提出 |
| **T2 反例** | `scope_evidence` に**異なる市場または異なる業種**の適用例が2件以上あるか | 例を追加、無理なら却下 |
| **T3 根本原因** | `failure_mode` が症状でなく機構の欠陥を指しているか（proposalが単発の指示でないか） | 失敗モードを掘り直す |
| **T4 重複・矛盾** | 既存ルールと重複／矛盾していないか（既存文言とのトークン重複で検出） | 既存ルールの改訂として出し直す |
| **T5 コスト** | SKILL.md本体の行数予算内か（既定500行）、追加ステップが2以上でないか | referencesへ移すか却下 |

判定は `PROMOTE` / `REVISE` / `REJECT`。**REJECTも記録を残す**（同じ議論の再演を防ぐ）。

## 昇格条件

- 原則: **別案件で2回以上再発**（`recurrence >= 2`）してから昇格。1回の違和感でルールを足すと肥大する
- 例外: **誤情報がレポートに載った種類の欠陥は1回で即時昇格**（`severity:"correctness"`）。
  これはコストより正確性が優先されるため
- 昇格先の優先順位: ①スクリプトのチェック項目（機械化できるなら最良）→ ②references → ③SKILL.md本体
  **機械化できる改善をSKILL.mdの文章で足さない。** 文章のルールは守られない確率が残る

## 反映と記録

`improvements/decision_log.md` に append:

```markdown
## 2026-08-22 I-004 → PROMOTE
- 失敗モード: 比較基準未明示（季節性）
- 反映先: scripts/check_b_ledger_report.py に B12 COMPARISON_BASIS 追加（機械化）
- 汎用性: T1〜T5 pass（scope: 日本株製造業 / 米国株小売）
- バージョン: v1.0.0 → v1.1.0
```

## 棚卸し（肥大の防止）

四半期に1回、または SKILL.md が予算行数の9割に達したら:
1. 各ルールの発火回数を `improvements/decision_log.md` から集計
2. **3案件連続で発火していないルールは削除候補**
3. 削除もバージョンを上げて記録（あとで復活させる判断ができるように）
4. 削除に迷うルールは references の末尾「アーカイブ」節へ移す（本体からは外す）

## 反省の対象を間違えない

- `[未調査|意図的]` は手落ちではない。これを改善候補に起票しない
- ユーザの好み（文体・粒度）は**ハーネスの欠陥ではなく設定**。`preferences` 系の変更として区別し、
  検証機構のルールと混ぜない
- 1件の指摘から「今後は常に◯◯を書く」と一般化しない。それは過学習であり、T2で落ちる
